# 工程过程与复核

日期范围：2026-11-02—2026-11-04，北京时间。本文按开发阶段组织；逐条原始可见交流见[对话日志](conversation.md)。用户反馈、自动测试与机器日志分别标明，不相互替代。

## 1. 阅读仓库、接收交接与开发环境

用户最初要求阅读比赛仓库及上游，接续队友工作；随后明确先等待交接文档，只检查开发板连接和 DSH／Antigravity 的模型与通信。交接就绪后，依据 `docs/项目完整交接.md` 进入板端联调。

开发对象为 BES2800BP／best1700 AP，主要使用 Windows 主机、Ubuntu-22.04 WSL 构建及 USB2UART 控制台。后续操作沿用已经验证的 AP-only 地址 `0x30190000`，保留 eMMC 配置、长期人设、音频资产及资讯缓存。COM 口和主机目录只是当时环境，不构成其他电脑的默认配置。

用户允许将合适的任务交给 DSH／Antigravity，以控制开销；之后还发生过主控与 DSH 之间的交接。模型、工具可用性及工作状态以各次检查为准，不把历史可用状态当成持续在线保证。

## 2. 热点与电脑供网联调

早期调试存在“热点能看到板子、手机能上网，但板端请求不通”的情况。关联到热点只证明 Wi-Fi 接入，不能单独证明 DNS、TLS 和模型请求可用。过程中对照了手机热点与电脑 PPP，用户曾追问当时语音到底走哪条网络。

排查还涉及 WPA2／WPA3 混合认证、改为仅 WPA2、电脑代理／TUN 的虚拟 IP、TLS 上传分块、TCP 参数、网络失败清理、语音超时和收音诊断。单项诊断或一次失败不证明其就是唯一根因。最后切换 5GHz、恢复默认传输参数后的完整问候与问答得到用户确认。

之后保留两种入口：手机热点直接供网，或电脑经串口 PPP 转发 IP。开发板仍承担音频、模型客户端、业务与存储；电脑供网不等于电脑代跑问答。

## 3. 唤醒与会话状态

用户先要求实现唤醒，再要求开机后自动进入检测；匹配唤醒词后播报“你好”，转入等待提问。最初使用“你好，openvela”，为排查失败增加过实际 ASR 文本和单次录音诊断。

用户将产品唤醒词改为“你好，夕夕”，并要求兼容 xixi 近音。用户随后确认听到本地问候及正确问答。空闲退出保持 60 秒，唤醒后没有问题则回到等待唤醒词。

后续仍出现安静环境下偶发唤醒失败，经过收音、实际转写和多轮测试继续修正，不能从一轮成功推出稳定识别率。当前正常唤醒和问答依赖云端 ASR；开机选网的两条本地模板不是通用离线唤醒引擎。比赛指定短语的复测也不能由“夕夕”别名通过替代。

## 4. 长期记忆、时间与主动资讯

用户提出板端保存长期人设，联网校时，每天七点准备兴趣相关资讯，存到板上，再询问是否播放。初始人设经用户确认，为热爱 AI、电子技术，偏好中文、开源及动手实践的大学生。

实现包括持久人设、联网 SNTP、按北京时间调度、日期缓存、许可状态与重播。人设修改先复述确认，分别验证过“取消”与“确认保存”；用户确认两类语音反馈，板端回读用于核对实际保存。

用户实际确认了收到资讯询问、回答“播放”后听到资讯，以及回答“暂不播放”后保持安静。针对句末标点及指令路由修正后，今天和昨天的新闻均得到用户完整播放反馈。日期不存在缓存时应明确说明，不用今天内容替代昨天内容。

没有现成服务器时，用户选择 GitHub Actions 采集与静态 JSON 方案。固定本地提示音用于问候、联网、询问及错误等常用语句，减少这些环节对实时 TTS 的依赖；动态答案仍需联网处理。真实早七点和长期无人值守观察继续作为验收边界。

## 5. 无需人工 RESET 的烧录方法

用户提供了曾成功执行的流程：正常停止 Agent，确认退出；通过 NSH 后台脚本延迟五秒执行 `reboot bootloader`；在同一个 Python 进程中立即关闭串口并启动 dldtool 接管同一端口。

下载器继承真实终端，不用 stdout 管道或 `CREATE_NO_WINDOW` 取代该路径。进入引导靠板端命令，`--reboot` 负责下载完成后的重启。串口连接的 DTR、RTS 为 False，不用于硬件复位。

只有 NSH 可响应时才具备软件流程前提。主控卡死、未开机与电脑 FTDI 串口桥异常是不同层的问题，不能将任何端口可见状态等同于能够软件烧录。后续多次记录观察到 SYNC 确认、`PROGRAMMING SUCCEEDED` 和退出码 0。

## 6. 飞书通知

用户选择开发板向本人飞书推送提醒、待办和资讯，完成官方 CLI 配置及授权。固定目标机器人测试发送经用户明确授权，之后用户确认收到测试消息。

板端通知接入鉴权、消息 API 回执和后台队列。用户已确认收到今天三条资讯、昨天资讯、待办清单，以及定时提醒的本地与飞书两种通知。口令包括“把今天的新闻发到飞书”“把昨天的新闻发到飞书”“把我的待办发到飞书”；入队提示不等于远端已接受。

后台等待问答空闲；说“再见”可退出，或等 60 秒空闲退出。队列为 RAM 队列，容量、去重和重试范围有限，停止／重启会丢失尚未发送的副本，原资讯、待办和提醒文件不因此删除。已尝试发送但状态不明的消息不自动无限重发。

## 7. 开机语音选网

用户将开机自动找热点改为：先本地询问“选择有线连接还是无线连接”，收到选择后再连接；成功说“连接成功”，失败说“连接失败”并重新询问。

为避免联网前依赖云端识别，开机两条口令使用本地个人模板；每类三个录入样本，并有独立验证及未知语句拒绝。个人语音模板留在板上，未公开上传。

过程中处理过“听到询问但没有成功播报”的情况，继续完成连接、SNTP 预算、串口所有权、PPP 接管与失败重问。应用、PC 待命、下载器和诊断程序不能同时占用串口，正常停止及清理结果需要核对。

## 9. PR #14 之后的三处缺陷复核

本地实际复现并修复以下问题；相关源码仍留在原工作区，未混入此次文档提交。

1. 新闻询问播放失败后仍保存 `asked=true`，导致后续被跳过。修复为已知失败时回退标记，30 秒退避重试，自动路径仍遵守 07:00—22:00，且失败不授予播放许可。
2. 自动监听完全停止时，旧输出预留使飞书队列一直滞留。增加成对后台保留接口，闲置或完全停麦时允许发送，不开启麦克风，活动会话仍推迟；SDK 新增 `0076`，本地补丁序列增至 60 项。
3. MiMo ASR、批量 TTS 和流式 TTS 构建 JSON 时缺少分配／附加结果检查，可能泄漏或发送缺字段请求。补齐所有权及失败清理；84 个预传输分配位置注入失败时返回 `-ENOMEM`、零 HTTP、零泄漏，原 51 处后续失败测试继续通过。

该阶段 88 项 headless Python、110 项 PC 工具检查通过，实际 C 使用 ASan／UBSan 等回归；复用 WSL 配置完成 22 步增量构建。AP 大小 1398504 B，SHA256 为 `544a7abb7dc7d19f6de7ea9e7a75e7a10b611c621f84f596738befafd10332f9`，自动烧录退出码 0。

烧录后的离线选网和本地提示就绪。配置与历史新闻的直接前后校验一致；人设两次回读与此前交付基线一致。本次烧录前单次控制台人设摘要异常，未据此声称该项直接前后哈希相同。新增真人业务仍保留待验收标记。

## 10. 拍摄前音量与口令兼容

用户要求提高喇叭音量。硬件播放维持已验证的 0 dB，增加可保存的软件幅度档位，范围 50—200，默认 100，板端设置为 150。150 是 PCM 幅度的 1.5 倍，不代表主观响度或功率的 1.5 倍；32 位缩放后限幅避免整数回绕，较响音频仍可能削波。

全部 s16 样本的 100／150 档缩放、极值、非法输入、默认值、配置失败及 DMA 回归通过。13 步增量构建与自动烧录完成，重启回读为 150；本地选网提示完整播放 145920 字节，随后恢复监听。实际听感由用户确认，机器日志不替代听感。

用户随后指出“飞书”常被转写成“脸书”。修复只在通知解析器的临时副本中兼容目的地后缀，今天、昨天和待办三类完整口令均接受；目标仍是配置中的飞书账号。否定、疑问、引用及复合语句仍不匹配，不把其他问答中的 Facebook 内容全局改写，也不宣称提高了 ASR 模型准确率。解析／队列／服务及晨报回归通过，12 步增量构建并烧录成功；现场别名语音发送未在该回执中验收。

用户要求清理拍摄用待办，已在板上保留原清单备份，清理前未完成 13 条，清理后 0 条。这是清空演示数据，不是把未做事项声称为已经完成。
