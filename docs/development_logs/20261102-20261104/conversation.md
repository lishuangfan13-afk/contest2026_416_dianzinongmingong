现在这个唤醒词是怎么实现的，怎么个逻辑


## 068 · 助手 · 回复

轮次 12，轮次开始：2026-11-02 14:51:14 +0800

当前实现是 **“检测到说话 → 云端转文字 → 板端匹配唤醒词 → 开启会话”**。

具体逻辑如下：

1. **收取一句话**
   开启自动语音后，板端先校准环境噪声，通过音量判断是否有人说话。说完后静音约 **1.2 秒**，结束本句录音。

2. **云端识别，再判断唤醒词**
   录音发给 MiMo ASR 转成文字，板端检查文字的**句首**是否为：
   - `你好，openvela`
   - `Hello，openvela`

   匹配允许常见空格、标点，以及英文大小写变化。

3. **唤醒后进入会话**
   - 只说唤醒词：播放本机提示音，等待提问。
   - 唤醒词后接问题：去掉唤醒词，直接处理问题。
   - 会话内继续提问：不必重复唤醒词。
   - 空闲 **60 秒**：回到等待唤醒。识别、处理和播放期间不会消耗这个空闲窗口。

例如：

| 说法 | 结果 |
|---|---|
| 未唤醒时说“一加一等于几” | 不进入问答 |
| “你好，openvela，一加一等于几” | 唤醒并回答 |
| “我刚才说了你好openvela” | 句首不匹配，不唤醒 |
| 会话内说“再见” | 结束会话，继续等待唤醒 |
| 说“停止监听” | 停止麦克风采集 |

**需要注意：等待唤醒时，检测到的语句也会发送给云端识别。** 因此唤醒速度受收句、网络和 ASR 耗时影响。整个交互采用半双工，处理和播报期间暂停收音。

目前麦克风已关闭，仅保留唤醒规则配置。实现说明见[仓库文档](https://github.com/open-vela/contest2026_416_dianzinongmingong/blob/dev-ai-contest-2026/docs/ASR唤醒短语.md)。

建议做成一个完整闭环：**长期人设 → 定时获取资讯 → 存入板子 → 询问播放 → 获得许可后播报**。

有一个关键前提：**目前电脑供网会话只有一小时**。要实现每天七点无人值守，需要改成常驻供网，或让板子独立连接 Wi-Fi；板子也需要持续供电。

1. **长期保存你的人设**

   复用现有用户偏好和长期记忆文件，例如保存：

   > 大学生，热爱 AI、电子，关注开源项目、嵌入式技术和适合动手实践的内容。

   重启后继续读取，修改人设不需要刷固件。新闻单独保存，避免每天的资讯挤进长期记忆。只有你明确要求，才更新人设。

2. **联网授时、七点准备晨报**

   每次联网或恢复连接后校准时间，并更新 RTC；每天按北京时间计算七点任务。

   建议 **06:55 预取，07:00 提示**。七点没联网，就在当天稍后联网时补取一次，不连续补播多天旧新闻。

3. **根据兴趣筛选真实资讯**

   从真实来源获取候选，再让 MiMo 筛选、整理，不能直接让模型凭记忆生成“今日新闻”。

   首批可以接入 [Hugging Face](https://huggingface.co/blog/feed.xml)、[Espressif](https://developer.espressif.com/blog/index.xml)、[Raspberry Pi](https://www.raspberrypi.com/news/feed/) 的官方 RSS。建议每天 **3～5 条、总长约 2～3 分钟**，每条保留发布时间、来源、链接，并说明与你的兴趣有什么关系。

   部分 RSS 很大，首版建议用电脑上的轻量采集器整理成小 JSON；板子负责最终筛选、模型请求、存储和交互。

4. **保存成功后再询问**

   新闻按日期和批次存入 eMMC，记录“待播、已询问、暂不播放、已播放”等状态。同一批内容不反复提醒，建议保留最近 30 天。

   设备空闲时询问：

   > “今天准备了三条 AI 和电子相关资讯，约两分钟，需要播放吗？”

   正在问答或播报时，等当前任务结束再询问。

5. **单独处理播放许可**

   提问结束后进入“等待新闻播放许可”，此时无需再说唤醒词：

   | 回应 | 行为 |
   |---|---|
   | “播放”“要听”“播放新闻” | 播放刚才这一批内容 |
   | “不要”“暂不播放” | 保留内容，当天不再主动催促 |
   | 60 秒没有明确回应 | 不播放，返回等待唤醒词 |

   “不要播放”必须按否定处理。许可判断由板端规则完成。以后也可以主动说“夕夕，播放今天的新闻”。

第一版先缓存文字，朗读仍依赖在线 TTS，回应许可也依赖目前的云端 ASR。开发顺序建议是：**人设保存 → 手动生成晨报 → 许可播放 → 七点调度与断线补取 → 无人值守运行**。

**一、先让串口回到可以执行 NSH 命令的状态**

如果正在运行电脑 PPP 供网，先正常停止：

```powershell
python tools/pc_link/launch.py --stop
```

等待供网程序结束、释放串口，再通过 USB2UART 连接板端控制台。原电脑使用：

- 端口：`COM3`，在其他电脑上按实际端口修改。
- 波特率：`921600`。
- DTR、RTS：False。
- 控制台提示符：`ap>`，也可能识别为 `nsh>`。

执行 `zhaoxi status` 检查助手状态。如果 Agent 还在运行，执行：

```text
zhaoxi stop
```

等待实际退出，观察 `[agent] Shutdown complete.`；必要时结合 `ps` 和 `zhaoxi status` 确认 Agent 已停止。然后执行 `sync`。

**注意：以上是通过串口发送到板子的 NSH 命令，不是在 Windows PowerShell 里直接执行。**

**二、在板上安排一个延迟执行的 bootloader 重启**

通过 NSH 依次发送：

```sh
echo sleep 5 > /tmp/zhaoxi_flash_reset
echo reboot bootloader >> /tmp/zhaoxi_flash_reset
```

临时脚本的实际内容为：

```sh
sleep 5
reboot bootloader
```

**三、立即关闭 Python 串口，并启动 dldtool**

这是整个方法最容易弄错的地方：

1. 后台延迟重启安排成功。
2. **马上关闭当前 Python／pyserial 的串口句柄。**
3. **立即启动 dldtool，让下载器占用同一个 COM 口并等待同步。**
4. 板端 5 秒到达，执行 `reboot bootloader`。
5. 下载器接住这次引导同步，继续下载。

**这几步应放在同一个 Python 程序内连续执行。** 不要把“安排重启”和“启动下载器”分成两次独立的 AI 工具调用，中间的调度延迟可能超过 5 秒，从而错过同步窗口。也不要在关闭串口后再等 5 秒才启动下载器。

```python
    "-b", "921600",
    "3",
    "-v",
    "--no-retry",
    "--reboot",

    "--set-dual-chip", "1",

    "--addr", "0x30190000",

```

- `"3"` 对应 **COM3**；该位置使用串口数字，按实际端口修改。
