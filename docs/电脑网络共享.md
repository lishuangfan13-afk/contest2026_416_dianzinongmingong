# BES 通过电脑提供网络

状态更新：2026-10-31。

自动语音仍是产品需求。当前按用户要求暂缓真人自动语音验收，本轮仅验证电脑供网，默认监听关闭。程序不会在后台自动开启麦克风；用户后续主动选择 [开始自动语音入口](../tools/pc_link/README_zh-cn.md) 才启用自动循环。以下镜像和功能结果按各次实际测试归属记录。

后续新固件曾有一次仅供网启动检查未通过：PPP 地址取得，但外部 DNS 返回 1，板端以 `rc=-113` 结束，尚未启动自动语音。旧主机程序只读到退出提示前缀而误报正常，现已修复。等待真实双向 IPCP 就绪的启动时序修复加入最终镜像后，下面的无麦克风实板复测已成功；早先失败仍按原测试记录保留。

**电脑转发网络已经支持三个核心功能的文字入口：实际问答、备忘写入回读、待办添加与指定完成、提醒到期和取消均取得实板证据。最终打包镜像又通过连续两次真实问答、更新后记录回读及正常退出；测试前后麦克风均关闭。自动多轮真人验收按用户要求暂缓，尚未通过。**

本方案通过现有 USB2UART 连接，由电脑转发 IP 数据。BES 负责 DNS、TCP、TLS、模型请求、工具、存储、调度和语音输出。测试结果不能证明板载 Wi-Fi 已修好，也不能证明接天线一定解决无线问题。

## 数据路径

```text
BES 麦克风 / 业务 / 调度 / 语音输出
              │
       BES DNS、TCP、HTTPS
              │
          PPP / USB2UART
              │
   Windows 串口转发 + 本机 WSL PPP
              │
      电脑当前可用的网络 → MiMo
```

电脑必须运行转发程序，USB 供电本身不会自动共享网络。板子另一个 USB 口当前没有启用 USB 网络设备驱动，本方案使用已验证的 FTDI USB2UART 通道。

API 凭据继续由板内运行时配置读取，转发程序不需要云端密钥。串口承载网络期间由一个程序独占；不要同时打开其他串口终端或烧录器。

## 构建依赖

在现有 headless 工作区基础上启用 `CONFIG_NETUTILS_PPPD`，保留 `CONFIG_NET_TUN`。主要内容包括：

- `app/zhaoxi/pc_link.c`：协商网络、临时路由与 DNS、限时对照或持续模式；退出时恢复设置。
- `app/zhaoxi/pc_control.c`：只绑定 PPP 地址，只接受直接连接电脑地址的有限业务命令。
- `0025-apps-pppd-bounded-pc-link-lifecycle.patch`：应用到 apps，提供 PC 直连生命周期、资源释放和按有效接收时间判断链路存活的逻辑。
- `0026-packages_ai_agent-accept-ppp-uplink.patch`：应用到 packages/ai_agent，让网络就绪检查接受实际启用的 ppp0，保留接口状态和无效地址检查。
- `0027-packages_ai_agent-rebuild-tools-after-restart.patch`：Agent 重启后重建工具注册，避免后续实例缺少工具。
- `0028-packages_ai_agent-observe-bes-tls-recv-errors.patch`：补充 BES TLS 接收错误观察。
- `0029-packages_ai_agent-continue-product-file-workflows.patch`：当前镜像中的文件业务继续处理修复，实际待办添加与指定完成通过。
- `0030-packages_ai_agent-bounded-product-tls-teardown.patch`：后续有界 TLS 停机修复；与 4235 镜像的文字业务结果分别记录。

完整构建还需现有 headless 补丁序列，以上不是独立安装清单。持续模式复用 zhaoxi 命令和工具；入口返回 0 只表示对应命令返回成功，异步业务须核对真实回答、文件回读、调度和播放结果。

## 电脑端准备与操作

当前实际验证环境：Windows、Python 3.14 与 pyserial、Ubuntu-22.04 WSL、Ubuntu ppp 2.4.9。WSL 的 `/dev/ppp` 已实际打开成功，虚拟网卡创建通过。

在 WSL 中安装 `ppp` 包后，在仓库根目录运行：

```text
python tools/pc_link/start.py --port COM3
```

等待 `PPP_UPLINK_READY`。当前程序在实际 ping action 返回成功后才输出此标记，并周期性复核；检查失败或确认过期后不再宣称 ready。该标记确认控制通道可达，不确认模型、ASR 或 TTS 业务。

默认会话最长一小时；有时限验收可传入 `--duration 1200`。在另一个终端使用：

```text
python tools/pc_link/control.py --status
python tools/pc_link/control.py --cmd --text ask 请简短介绍自己
python tools/pc_link/control.py --cmd --text note 明天带学生证
python tools/pc_link/control.py --cmd --text todo add 交作业
python tools/pc_link/control.py --cmd --text todo list
python tools/pc_link/control.py --cmd --text remind in 60 喝水
python tools/pc_link/control.py --cmd listen start
python tools/pc_link/control.py --cmd listen stop
python tools/pc_link/control.py --quit
```

上述待办文字流程已经实板验证。录音示例仍是排查入口，不代表完整语音输入已经通过。默认不带 `--text` 的业务使用现有语音通道。

到达会话期限时，程序发送 quit，同时继续转发双向数据，等待板端恢复控制台；没有恢复确认会报告失败。调试记录保存在已忽略的 `out/pc_link`。原始串口、音频和工具回复可能含私人内容，不应上传公开仓库。

正常退出时删除本机通道令牌，清理本程序增加的 WSL 转发规则，并恢复此前转发开关。状态文件记录收发字节、最近收发时间、控制检查和网关清理结果。

## 本轮修复的通信问题

此前单次 DNS 成功后，HTTPS 曾被 Wi-Fi 专用就绪检查阻止；0026 接受实际可用的 PPP 接口，随后原生 HTTPS 请求通过。

电脑端建立本机连接时的 10 秒超时曾被沿用到持续接收，空闲后接收线程退出，造成后续电脑→板子数据不再转发。当前程序连接后清除接收超时，在收发线程失败时报告，不再继续保持虚假的就绪状态。

PPP 与控制台共用 UART 时需要正确处理控制字符、终端模式和链路存活。当前主机转义控制字符，板端临时使用 raw 终端模式。PC 直连模式按最近有效接收的时间判断失联，避免把 TLS 握手期间短时间发送多帧误判为断线。退出检查、工具重建和上述修复已参与这轮实际业务会话。

后续重点是修复并验收录音启动顺序，完成真人 ASR 输入与三项功能的完整语音操作，确认新音量，并验证正常停机。板载 Wi-Fi 是否能稳定通信仍需单独验证，不是本方案通过的前提。
