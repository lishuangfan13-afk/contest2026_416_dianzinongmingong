# 对话语音连续播放

2026-11-03 实板定位到电脑 PPP 下的供音速度不足：旧流式回答分别接收 576000 字节和 1136640 字节 PCM，首包后接收跨度为 16460 ms 和 33084 ms，约 34–35 kB/s；24 kHz、单声道、16 位播放需要 48000 B/s。640 ms 初始缓冲与 64 KiB 队列无法填补长回答的持续速率差，播放会反复等待网络。

电脑有线模式现在先接收一段回答的完整 SSE 音频，验证结束标记和 PCM 完整性，再把内存中的数据交给原播放队列。最大 5760000 字节（120 秒 PCM），按需扩容，收包失败、坏数据、超限或内存不足时释放数据并返回错误，不把已收到的前缀当作完整回答播放。接收保留原 180 秒请求时限，每个播放块保留停止和错误检查。无线保留原流式播放；开机个人识别模型和提示音不受影响。

此策略增加有线模式开播前的等待。实板 18.88 秒回答在 28.112 秒接收完成后播放，17.12 秒回答在 24.632 秒接收完成后播放。它解决的是播放中的断音，不会让串口吞吐或云端生成变快。无线固定句本轮首包等待 11.055 秒，也说明开始说话前的网络延迟应与播放卡顿分别判断。

SDK 补丁 0075 使已进入接收／播放的 TTS 不被“未收到回答”的 180 秒守护误判；缺少回答时的原超时保持。活跃输出自身仍受 HTTPS 请求时限、120 秒 PCM 上限、DMA 超时及取消控制。实际 C 自动语音测试覆盖活跃 speaker 超过回合等待时限后继续运行、正常释放并恢复采集，以及无 speaker 时仍超时停止。

播放器现在在关闭时输出 `BESPCM timing`，仅含字节数、采样率和耗时，不含语音内容。`play_ms` 是第一块到最后一块成功 DMA 的跨度，`ideal_ms` 是音频自身时长；`gap_ms` 是块间间隙之和，`max_gap_ms` 是最大单次间隙。失败的首次 DMA 不会产生下溢的虚假播放跨度。

真实问答后自动语音保持 enabled／running，恢复 accepting_speech，控制通道仍响应。这些指标支持本轮样本播放连续，并非对所有网络或所有回答的保证；真人听感与长期运行需持续观察。

离线回归使用实际 MiMo provider、SSE、JSON 和 base64，覆盖慢速分片、PC 完整校验后输出与 Wi-Fi 边收边播、字节顺序、结束条件、HTTP/协议错误、接收／播放取消、完整 5.76 MB 上限及超限拒绝。51 个收包／解析／缓冲分配失败位置和 SSE 创建失败均检查释放；ASan、UBSan 和泄漏检查通过。SDK 完整 59 项补丁回放与实际构建源一致。
