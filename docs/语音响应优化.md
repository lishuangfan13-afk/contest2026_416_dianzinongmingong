# 语音首声与连续播放优化

2026-11-01。本轮已完成完整构建、软件重启烧录和固定文本实板测试，交付选择 `4e22a196…` 固件与更新后的电脑供网工具。首声明显提前，三个文字请求均完成；短句与模型回答仍有播放欠载，因此连续播放与最终现场听感尚未全部验收。麦克风保持关闭，本轮没有收取无人值守语音。

## 修改了什么

原 MiMo TTS 适配虽然名为 stream，实际先取完整 JSON、解码整段 PCM，再送播放器。0038 提供有界的 HTTPS 正文增量接收，产品适配改读 SSE 的 `choices[0].delta.audio.data`。0039 使用固定 64KiB PCM 队列，让网络接收与 DMA 播放同时推进；连接仍由原调用任务拥有。

普通 `mimo-v2.5-tts` 支持流式音频，当前输出采用 24kHz、PCM16LE、单声道。官方 Token Plan 端点的受控固定文本检查，流式首音频约 1.1～1.3 秒；这只是电脑端提供方结果，不是板端首声或完整语音问答耗时。[小米语音合成文档](https://mimo.mi.com/docs/en-US/quick-start/usage-guide/audio/speech-synthesis-v2.5)

0040 对本产品官方 MiMo `mimo-v2.6-flash` 的普通和工具请求显式关闭深度思考，其他模型、供应商、工具 schema 和输出上限保留原行为。实际耗时仍以板端请求为准。[小米深度思考文档](https://mimo.mi.com/docs/en-US/quick-start/usage-guide/text-generation/deep-thinking)

首版流式固件首声提前，但用户听到停顿。随后沿播放与传输两端修复：

- 播放侧合并短碎片并记录队列欠载；BES 后端从轮询 DMA 改为中断信号量唤醒，0043 将 NuttX PCM 消费线程设为 RR 优先级 110，DMA 累计时间已接近音频理论时长。
- 0044 将 TLS 接收的暂时无数据、超时切片恢复为可重试状态，保留绝对截止时间；0045 将首播缓冲调整为 30,720 字节或最多 640ms，短音频在 EOF 即时冲刷。
- 电脑转发取消每 128 字节固定暂停，按最多 512 字节同步写入并保留背压、停止检查，接收及时转发小 ACK。apps 0042 批量接收串口，0046 为电脑直连 PPP 协商 asyncmap 0，0047 将完整帧一次提交，减少普通日志插入帧内的机会。电脑转发与网关 TCP 两端同时启用 `TCP_NODELAY`；普通 modem 路径保留原行为。

交付固件大小为 **1,329,688 字节**，SHA256 为：

```text

```

首声从进入板端 `voice_channel_speak` 计到第一段 PCM 进入实际播放回调，属于软件测量，尚未使用独立声学计时。命令入队返回不算播放完成；成功记录等待了 `speak done` 与实际 PCM 统计。

每格是一条实板请求，不是多轮平均值。合成音频时长和网络到达时间会变化，不能将单次差值当作稳定提速承诺。交付版本的短句有 6 次欠载、累计 703ms；较长句零欠载；文字问答有 4 次欠载、累计 1981ms。所有 PCM 字节均完整交给播放，仍不能据此宣布没有卡顿。

文字问答“请用一句话解释什么是待办清单”的模型生成耗时 **1.866s**，进入 TTS 后 **1.999s** 首声，文字请求至播放完成 **13.060s**。这个结果不包含收音、1.2 秒封句和 ASR，不是完整语音问答响应时间。

同一固件还做了一次私有主机 75,000 字节／秒平滑发送对照：短句零欠载，长句 3 次、234ms，文字问答 2 次、249ms。它没有消除全部欠载，未改为生产默认参数。该轮模型生成耗时 8.656s，单次对照无法证明这一变化由限速造成。交付仍使用仓库默认主机工具。

## 证据与保留边界

[实板对照记录](bringup_logs/20261101_voice_latency.json) 保留全部中间版本、默认交付和私有实验的首声、PCM 字节数、DMA 时间、欠载次数、累计等待和退出状态。交付与平滑发送对照在测试前后均确认自动语音关闭、采集帧数与 ASR 次数为零，并正常退出。历史 `cb080953…` 的失败测试缺少结束快照，JSON 明确记为空，未补造结果。

PPP 头部对照显示，asyncmap 0 将电脑到板子的串口字节／网络字节比由约 1.177 降到 1.022；SACK 仍然存在，表示数据缺口或重排尚未消除。抓取没有时间戳，不能据此确定缺口发生在公网还是串口，也不能推导重传耗时。扩大 UART 接收缓冲的配置尝试没有生效：完整构建后的 `g_uart0rxbuffer` 仍为 4095 字节，来自预编译 BSP 的 `bes_serial.o`。该配置已撤回，相关候选镜像没有烧入，没有把 16KiB 接收缓冲写成交付成果。

本轮通过 55 项主机转发回归、32 个 SDK 补丁与 23 个源码文件的回放比较，以及 5 组 apps 回归和补丁回放。真实 TLS 分片、SSE/base64、播放队列、DMA 完成唤醒、模型参数和 PPP 行为有源码检查。两份云端 SSE 经实际 C 解析器解码，与标准解码的 PCM 逐字节相同；原始返回、密钥和音频不进入公开仓库。代码检查通过、文字请求完成和现场听感通过是不同结果。

ASR 仍在封句后整句上传，忙时不支持插话。三个业务的真人语音验收、断电授时和板载 Wi-Fi 状态不因本轮 TTS 优化而自动视为通过。网络取消在正文或 PCM 回调间检查；首包未到或网络长时间静默时仍需等待网络错误或截止时间，不能承诺整个请求即时退出。

本轮已冻结上述交付，不再追加底层改动。开发板固件和 `tools/pc_link` 主机文件应一起更新，以使用相同的转发与 PPP 协商条件。最终固件的现场听感仍需有人在场确认。
