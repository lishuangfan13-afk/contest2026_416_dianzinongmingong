# 语音首声与连续播放优化

朝夕的语音输出采用增量接收和有界 PCM 队列，让网络下载与 BES DMA 播放同时推进。电脑供网侧同步优化串口转换和 ACK 转发，减少传输中的等待。

本文保留 2026 年 11 月 1 日 `4e22a196…` 等历史镜像的优化记录。当前固件与安装方法见 [BES 固件构建与验收](BES固件构建与验收.md)。

## 播放路径

原适配先接收完整 JSON、解码全部 PCM，再进入播放。现在使用 SSE 增量接收 `choices[0].delta.audio.data`，由实际 C 解析器处理事件分片、base64 和 PCM 样本边界。

- 固定 64 KiB PCM 队列连接网络接收与播放线程，保留背压、取消和错误清理。
- BES 播放由 DMA 完成中断唤醒，消费线程使用 RR 优先级 110。
- 首播预缓冲为 30,720 字节，约 640 ms；短音频在 EOF 即时提交。
- TLS 的暂时无数据采用接收时间片重试，同时保留总截止时间。
- MiMo 产品文本请求关闭深度思考，以简短口语回答为主。

当前 MiMo TTS 输出为 24 kHz、PCM16LE、单声道，接口资料见 [小米语音合成文档](https://mimo.mi.com/docs/en-US/quick-start/usage-guide/audio/speech-synthesis-v2.5)。

## 电脑供网优化

Windows 转发取消每 128 字节的固定暂停，按最多 512 字节同步写入并及时转发 ACK。apps 端批量读取 UART、协商 asyncmap 0，并将完整 PPP 帧一次提交。电脑内 TCP 两端启用 `TCP_NODELAY`。

这些改动与开发板固件配套使用，相关顺序见 [补丁说明](../patches/README.md)。

## 历史实板测量

首声计时从进入板端语音合成入口到第一段 PCM 进入实际播放回调；完整语音交互还包括收音、封句和 ASR。

| 对照版本 | 短句首声 | 较长句首声 |
| --- | ---: | ---: |
| `c19ddd07…`，整段 TTS 与旧转发 | 4.767 s | 8.601 s |
| `8f7f374d…`，首版流式 TTS | 3.126 s | 2.850 s |
| `4e22a196…`，播放与转发优化 | 2.795 s | 2.354 s |

上述数值各对应一次请求。`4e22a196…` 大小 1,329,688 字节，SHA256 为：

```text
4e22a19662433dca3acc301e380a68187efd2bf73d1cd3fc492fd090620d06f2
```

该镜像的短句记录到 6 次队列欠载、累计等待 703 ms；较长句为零；文字问答记录到 4 次、累计 1,981 ms。当前继续优化长时间接收和播放的连续性。

一次“用一句话解释待办清单”的文字问答中，模型耗时 1.866 s，进入 TTS 后 1.999 s 提交首段 PCM，请求到播放结束 13.060 s。语音输入的完整响应时间另加本地收音和 ASR。

同固件的 75,000 字节／秒平滑发送实验中，短句零欠载，较长句 3 次／234 ms，文字问答 2 次／249 ms；生产入口仍使用仓库默认参数。PPP 协商优化将电脑到板子的串口字节／网络字节比由约 1.177 降至 1.022。

## 检查与记录

[实板对照记录](bringup_logs/20261101_voice_latency.json) 保存各镜像的首声、PCM 字节、DMA 时间、队列欠载和退出结果。公开记录保留历史版本，便于对照后续改动。

源码检查覆盖 TLS 分片与截止、SSE/base64、PCM 队列、DMA 唤醒、模型参数和 PPP 帧处理。两份云端 SSE 通过实际 C 解析器解码，与标准解码的 PCM 逐字节一致。当前检查入口汇总在 [构建与验收](BES固件构建与验收.md)。

ASR 在本地封句后整句上传。语音流程采用半双工，等回答播放结束再说下一句。连续自动语音的响应与恢复是当前优化重点，日常演示使用电脑供网、文字输入与语音播报。
