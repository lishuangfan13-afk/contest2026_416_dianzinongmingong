# 权限收窄的多智能体派工

## 何时使用

- 任务较大，需要拆给多个 AI 会话（不同工具或不同会话）接力/并行
- 主控（人或主会话）负责 review，执行交给子会话
- 仓库有安全红线（如密钥、公共仓纪律），不能让执行方随意操作

## 模式总览（提炼自本项目 34 段会话日志的实际派工模板）

每个子任务的任务书包含五个固定要素：

```text
① 角色声明    "你是嵌入式 C 工程师 / 文档工程师 / 安全修复工程师 / 只读调查员"
② 权限边界    "允许读写文件，但禁止执行任何 git 命令" 或 "READ-ONLY，不修改任何文件"
③ 文件所有权  "You own ONLY these files: <精确路径列表>"（其余一律禁碰）
④ 证据要求    "Cite file:line for EVERY claim"（调查类任务）
⑤ 交付格式    改完报告 / 输出报告文档 / 产出 patch 文件
```

## 三类标准任务书

| 类型 | 权限 | 用途 | 真实案例 |
|------|------|------|----------|
| **只读调查** | 不改任何文件 | 动手前建立事实基础 | 调查 ai_agent 框架规划 2 个新功能；LVGL 应用功能规划 |
| **限定写** | 只拥有指定文件，禁 git | 具体编码/修复 | 修复 cron.json 与框架 schema 不匹配；单文件修改 zhaoxi_ui.c |
| **产出型** | 只写指定输出路径 | 文档/补丁生成 | 生成 format-patch；生成作品介绍 docx |

## 派工纪律（每条都有真实教训）

1. **git 权限永远集中在主控**。子会话"改完报告即可"，commit 由主控核对 diff 后统一执行——曾发生 AI 用默认身份提交、作者归属错误，事后重写成本很高。
2. **文件所有权要精确到路径**。"你可以改 app 目录" 太宽，曾出现子任务把不该动的文件一并改了。一个任务书只给一个/一组强相关文件。
3. **敏感操作单独派工**。清除明文 API key 是一次独立的安全任务书，明确"公开仓、已泄露、只清除不改功能"，避免在功能任务里顺手处理导致遗漏。
4. **先调查后动手**。写任务之前先派一轮只读调查，把 file:line 事实写进任务书背景——子会话不需要重新摸索，命中率显著更高。
5. **换行符写入任务书**。"保持原文件换行符（LF）"要显式写——AI 工具整文件重写时曾把 LF 写成 CRLF，产生 764 行假 diff。
6. **验收闭环**。子会话报告 ≠ 完成。主控逐文件看真实 diff（先 `core.autocrlf=false`）、按交付清单逐条核对，发现过度承诺（如 README 写了实际没有的能力）当场打回修正。

## 效果（实测口径）

本项目后期的主要功能提交（UI 数据联动、daily 调度补丁、部署工具链、安全清理）均以该模式完成：主控拆任务 → 3–6 个收窄会话执行 → 主控验收修正 → 统一提交。每段会话日志（仓内 `logs/`）都保留了完整任务书与执行记录，可复现。

## 任务书模板

```text
你是<角色>。任务：<一句话目标>。
权限：<READ-ONLY | 允许读写文件但禁止任何 git 命令 | 只写以下输出路径>。
你只拥有这些文件（其余禁碰）：
- <路径1>
- <路径2>
背景：<file:line 级事实，来自上轮只读调查>
交付：<格式>。改完报告即可，不要 commit。
```
