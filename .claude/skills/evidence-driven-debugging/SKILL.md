# 证据驱动调试

## 何时使用

- 真机行为与预期不符（触摸无响应、显示异常、网络不通）
- "改了代码但烧上去没变化"类问题
- 需要给另一个 AI/工程师描述问题时（要求先拿出证据）

## 核心原则

1. **只读调查先行**：改代码之前，先做一轮只读调查（读源码/配置/串口日志），产出一份带 file:line 的事实清单。调查任务显式声明"READ-ONLY，不修改任何文件"。
2. **file:line 强制**：任何结论必须落到 `文件:行号`，"我记得大概是"不算证据。
3. **对比排除法**：找一个"能工作的参照物"逐项对比差异（见触摸案例）。
4. **不盲目重烧**：每次烧录前先问"这次烧录能验证什么疑点"，串口上能看到答案才值得烧。

## DIAG 自诊断层（可移植到任何 LVGL/NuttX 应用）

为了让每次烧录都物尽其用，UI 内置串口诊断输出，把关键疑点全部暴露：

| 标签 | 含义 | 验证目标 |
|------|------|----------|
| `DIAG READY` | 启动自检：数据源就绪数、字体数量 | 启动完整性 |
| `DIAG FILE <name>=<value>` | 数据源文件内容变化 | UI↔Agent 文件解耦链路 |
| `DIAG TOUCH x=.. y=..` | 触摸坐标与状态 | 触摸链路 |
| `DIAG NAV idx=N` | 屏幕切换索引 | 滑动/按钮导航 |
| `DIAG ALIVE N` | 30 秒心跳 | 检测卡死 |

一次烧录即可回答：程序活着吗、触摸通吗、切屏了吗、文件读到了吗——避免"改了烧、烧了看"的循环。

## 疑难案例库（全部真实，含根因与修法）

### 案例 1：zhaoxi_ui 触摸完全无响应
- **现象**：`/dev/input0` 存在且权限正常、lvgldemo 下触摸正常、zhaoxi_ui 下 `cat /dev/input0` 无数据。
- **排除**：硬件（lvgldemo 正常）、设备节点、defconfig（三个相关 CONFIG 均已开）、初始化代码（`input_path="/dev/input0"` 正确）。
- **根因**：lvgldemo 用 `lv_nuttx_uv_loop`（libuv 事件循环，文件描述符回调驱动输入），zhaoxi_ui 用 `lv_timer_handler` 轮询——**输入驱动的注册方式差异**。
- **修法**：zhaoxi_ui 通过 `lv_nuttx_init` 自行注册输入设备，不依赖 lvgldemo 的初始化路径。
- **方法论**：差异对比要对比到**初始化方式**这一层，而不是停在"配置都对"。

### 案例 2：时钟停在 1970，所有 HTTPS 不可用
- **现象**：TLS 握手失败、`ask` 无响应。
- **根因**：设备无 RTC，`vela_tls.c` 硬编码 `clock_settime(1772275200)`（2026-02-28），过期后证书时间校验失败。
- **修法**：三级时钟策略——HTTP Date 头对时（首选）→ 编译期 `__DATE__/__TIME__` 回退 → 保守兜底时间戳（补丁 0001）。

### 案例 3：修改 rcS 后烧录无变化
- **现象**：defconfig/rcS 都改了，板上仍跑旧行为。
- **根因**：CMake 缓存了预处理后的 rcS。
- **修法**：删 `cmake_out/aos_evb_ap/etc/init.d/rcS` 后重编。**教训：构建系统缓存是"改了没生效"的第一嫌疑。**

## 输出规范

调查结束后，产出固定格式的事实清单：

```text
## 事实清单（file:line）
1. xxx：src/xxx.c:123
2. ...
## 推断（标注置信度）
...
## 建议验证步骤（每步说明预期串口输出）
...
```
